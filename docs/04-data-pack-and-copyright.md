# 04 — Норм-пакет, копирайт и разделение «ссылки vs значения»

## 4.1 Позиция по копирайту (критично)

Таблицы IEC 60364 защищены авторским правом IEC. Прототип **не скрапит и не воспроизводит
лицензионные таблицы**. Поставляется **синтетический норм-пакет** (`data/packs/iec-stub.json`,
`meta.status = "illustrative"`):

- **структура** повторяет организацию таблиц IEC (метод × материал × изоляция × число жил ×
  сечение и т.д.), чтобы лицензионные данные подключались один-в-один;
- **значения — синтетические**, сгенерированы независимо и **намеренно не совпадают** с
  опубликованными рядами IEC/BS 7671 (round-числа, свой масштаб); `source_note` явно
  фиксирует «SYNTHETIC, NOT derived from IEC»;
- **ссылки** (Citation: стандарт/пункт/таблица) — **реальные** идентификаторы.

> **Почему синтетические, а не «репрезентативные реальные».** Реальные значения таблиц
> (ряд ампакитности метода C, k=115/143/76/94 из Table 43A, поправки B.52.14/B.52.17) — это
> и есть охраняемое таблицами выражение; поставлять их под ярлыком «плейсхолдер» было бы и
> воспроизведением копирайта, и ложной пометкой. Поэтому значения переопределены синтетически.

## 4.2 Разделение «ссылки реальны — значения синтетические»

Центральное для честности заявления о прослеживаемости:

| Аспект | Статус в прототипе |
|---|---|
| Механизм цитирования (какой пункт/таблица применён на каждом шаге) | **реальный, полный** |
| Формулы и условия координации/поправок/адиабатики (методология) | **реальные** (общее инж. знание) |
| Правило координации `I2 ≤ 1.45·IZ` и коэффициенты I2/In по классу | **реальные правила** (цитируются) |
| Числовые значения таблиц (It, ka, kg, k) | **синтетические** (не из IEC) |
| Соответствие значений реальному тексту IEC | **вне объёма** — нужны лицензионные данные |

**Обязательная формулировка (в отчёте и README):**
> Механизм прослеживаемости реален: каждый шаг ссылается на конкретный пункт/таблицу
> IEC 60364, и применяется реальная методология координации/поправок/адиабатики. Числовые
> значения таблиц в комплекте — СИНТЕТИЧЕСКИЕ (не выведены из IEC) и подлежат замене
> лицензионными данными IEC через подключаемый норм-пакет. Пометки PASS/FAIL отражают
> арифметику относительно синтетических значений, а не соответствие реальному стандарту.

**Структурное усиление (B12):** `SizingResult.data_provenance_note` — обязательное поле,
заполняемое по `data_pack.status`: при `illustrative` содержит формулировку выше, при
`licensed` — пустую строку. `report.render_markdown` ОБЯЗАН его печатать. Тест проверяет:
нота присутствует при `illustrative` и исчезает при `licensed` (см. `06 §6.6`).

**Проксимальность к вердиктам (B13):** таблица `checks` в отчёте предваряется маркером
«вердикты вычислены относительно синтетического пакета», когда `status=illustrative`.

## 4.3 Подключаемость (замена на лицензионные данные)

Загрузчик `load_data_pack(path) -> DataPack` (`03 §3.7`) читает JSON по контракту `03 §3.10`
и валидирует его. Замена стуба на лицензионный пакет:

1. Получить лицензию IEC на нужные части 60364-5-52 / -4-43 / -5-54.
2. Заполнить тот же JSON лицензионными значениями; выставить `meta.status = "licensed"`.
3. Указать путь: CLI `--data-pack FILE.json` (`03 §3.8`) или API `size(request, data_pack=…)`.
4. Отчёт автоматически убирает провенанс-ноту и маркер (по `status`).

Код движка не меняется — только данные.

## 4.5 Валидация пакета при загрузке

- Все ключи `k_material`, `ambient_correction[insulation]`, `grouping_correction`,
  `device_classes[class]`, `ampacity[method][material][insulation][n]` и `citations`
  присутствуют для запрошенной комбинации; иначе — `DataPackError` с указанием, чего не
  хватает (без «угадывания»).
- `ambient_temp_c` / `grouping_circuits`: **точное** совпадение ключа (`pack_key`) или
  `DataPackError` (off-table политика v1, `03 §3.3`).
- `meta.status ∈ {illustrative, public_standard, licensed}`; числовые значения > 0; ряды по
  возрастанию.

## 4.6 Мульти-пак и статус `public_standard` (docs/12 §1.1–1.2)

Помимо `illustrative` (синтетика) и `licensed` (нужна лицензия IEC), есть третий статус —
`public_standard`: значения внесены из **реального, бесплатно доступного государственного
стандарта** (не IEC — свой копирайт-режим, обычно свободная публикация актом госоргана).
Первый такой пакет — `pue-rk` (ПУЭ РК, приказ Министра энергетики РК №230 от 20.03.2015,
https://adilet.zan.kz/rus/docs/V1500010851 — полный текст правового акта в открытом доступе).

**Протокол ввода (человек в контуре, обязателен для каждого нового `public_standard`-пакета):**

1. Значения вносятся **только кодом**, парсящим официальный источник (напр.
   `scripts/extract_pue_rk.py` — скачивает HTML и извлекает таблицы), никогда «по памяти» LLM
   (правило `12 §0.2`). Каждая таблица пакета несёт в `_citation`: `source_document`,
   `source_table`, `entered_by`, `verified_by`.
2. `scripts/pack_review.py` печатает извлечённые таблицы для сверки глазами инженером и
   прогоняет автоматические проверки: монотонность тока по сечению, монотонность поправочных
   коэффициентов, выбросы (скачок > 60% между соседними сечениями помечается как подозрительный).
   Подозрительные значения обязательно сверяются с печатной редакцией стандарта перед фиксацией
   пакета — это единственная точка, где ревью человеком не опционально.
3. Golden-кейсы для нового пакета пересчитываются **независимо** через `scripts/reference_calc.py
   <pack-name>` (вторая, не связанная с движком реализация формул) — ожидаемые значения не
   копируются из вывода самого движка.
4. Off-table честно: если стандарт не покрывает какой-то метод прокладки/материал/изоляцию —
   пакет просто не содержит этот раздел, движок вернёт `DataPackError` при обращении (никакой
   экстраполяции/угадывания).

**Частичное покрытие таблицы (реальные паки ≠ полностью заполненный синтетический стуб).**
Синтетический `iec-stub` заполнен по всему ряду сечений для каждой комбинации; реальный
источник — нет. У `pue-rk` v1 (методы C+B1, Cu+Al, PVC — docs/12 §1.1) таблицы покрывают
ряд сечений лишь частично: например, метод B1 («в трубе») в Табл.4/5 обрывается на 120 мм²,
алюминий начинается с 2.5 мм². Поэтому свип движка (`engine/sizer.py`) перебирает **только
покрытые сечения** — предикат `DataPack.has_ampacity(method, material, insulation, n, S)`
(docs/03 §3.7) отфильтровывает отсутствующие, а не роняет расчёт на первом же пропуске:

- сечение вне таблицы для данной комбинации → **не является кандидатом** (пропускается);
- если нагрузка не удовлетворяется даже на **крупнейшем покрытом** сечении → честный `FAIL`
  на этом сечении (а не краш на бо́льшем непокрытом);
- если комбинация метод/материал/изоляция отсутствует **целиком** → `DataPackError`
  (тот же честный off-table, что и в п.4).

Важно: `has_ampacity` гейтит **только** пропуск сечения; off-table по `ambient_temp_c` /
`grouping_circuits` (реальные входы, которые пак не может обслужить) по-прежнему жёстко
падает `DataPackError` внутри `corrected_ampacity` — это не «дырка в покрытии», а ошибка
запроса, её нельзя молча проглатывать.

**Провенанс-нота** для `public_standard` (`models.provenance_note_public`, docs/03 §3.7):
«значения внесены из публичного государственного стандарта ⟨source_document⟩; документ не
воспроизводится целиком, только цитируется по пунктам/таблицам; транскрипция проверена
инженером (см. `_citation.verified_by`)». В отличие от `illustrative`, вердикты PASS/FAIL
**соответствуют реальному стандарту** (в пределах точности транскрипции) — маркер «вердикты
относительно синтетики» (`04 §4.2`) для `public_standard` не печатается.
