# 15 — Copilot щита: инструменты и proposal-контракт

> Статус: контракт фазы 5. Читать вместе с `docs/03`, `docs/11`, `docs/12 §5`,
> `docs/14` и `docs/15-project-persistence.md`.

## 15.1 Граница ответственности

Copilot — рекомендательный оркестратор над типизированным проектом. LLM выбирает
инструменты, извлекает пользовательское намерение и предлагает операции. Все инженерные
значения до/после (IB, S, In, ΔU, итоги и findings) создают только существующие
детерминированные функции. Серверный агент не вызывает `ProjectStore`, не записывает в
Neon и не применяет proposal.

Один запрос ограничен шестью ответами модели и 45 секундами монотонного времени. Лимит,
таймаут, ошибка модели или инструмента завершают цикл структурированным частичным ответом;
частично построенные операции не применяются.

## 15.2 HTTP-контракт

`POST /api/copilot` принимает:

```json
{
  "project": {"schema_version": 2},
  "message": "добавь цепь и проверь ввод",
  "history": [{"role": "user", "content": "..."}]
}
```

Проект проходит общий закрытый `Project`-контракт до вызова LLM. История допускает только
роли `user`/`assistant`, не более 20 сообщений; пустое сообщение отклоняется.

Успешный ответ:

```json
{
  "ok": true,
  "reply": "...",
  "proposal": {"ops": [], "diff": {}},
  "model": "provider/model",
  "provenance_ok": true,
  "unverified_numbers": [],
  "incomplete": false,
  "error": null
}
```

`proposal` равен `null`, пока модель не вызвала `propose_changes`. Без ключа возвращается
`ok=false`, `error=no_key` и русское сообщение о доступных ручном редактировании,
детерминированном расчёте и нормоконтроле. Для лимита, таймаута и ошибки используются
стабильные коды `iteration_limit`, `timeout`, `model_error`, `invalid_tool` и
`invalid_proposal`; это не успешный fallback.

## 15.3 Реестр инструментов

- `get_board_state()` — свежий `project-report` и канонические идентификаторы цепей.
- `parse_circuit({text})` — существующий LLM intake; возвращает типизированный
  `SizingRequest`, но ничего не рассчитывает и не сохраняет.
- `compute({request})` — свежий `SizingResult` выбранного проектом norm-пака.
- `run_normcheck()` — свежий детерминированный отчёт R01–R10.
- `propose_changes({ops})` — валидирует операции, строит новый проект только в памяти и
  завершает цикл детерминированным diff.

Результат каждого инструмента возвращается модели как JSON. Неизвестный инструмент,
невалидные аргументы и повторный `propose_changes` завершают запрос ошибкой; агент не
пытается угадать исправление.

## 15.4 Операции proposal

Операции — закрытое объединение:

- `add`: обязателен `request`; необязательны `circuit_id`, `ref`, `meta`. При отсутствии
  id сервер выдаёт первый свободный детерминированный `copilot-N`.
- `edit`: обязателен существующий `circuit_id`; меняются только явно переданные
  `request`, `ref` и/или `meta`.
- `delete`: обязателен существующий `circuit_id`; дополнительные поля запрещены.

Неизвестный id не становится добавлением. Повторные id, пустой edit и выход за число мест
щита отклоняются до расчёта. После операций проект повторно проходит общий `Project`-контракт
и топологическую проверку. `result` и signoff не принимаются от модели; новые и изменённые
цепи получают `UNSIGNED_ADVISORY` и не наследуют клиентский snapshot как истину.

## 15.5 Детерминированный diff

Оба состояния пересчитываются одним выбранным norm-паком через `build_project_report`.
Для затронутой цепи diff содержит тип изменения и `before`/`after` с полями
`section_mm2`, `protection_in_a`, `design_current_a`, `voltage_drop_pct`, `status`.
Board diff содержит `status`, `connected_kw`, `imbalance_pct` и `incomer_md_a` до/после.
Ответ сохраняет `data_identity`, `data_provenance`, дисклеймер и `UNSIGNED_ADVISORY` из
свежего состояния после proposal. Порядок ops и circuit diff стабилен.

## 15.6 Числовой провенанс reply

Числа в финальном тексте LLM разрешены только если они встречаются как типизированные
числовые листья результатов инструментов или обоих project-report. Идентификаторы правил и
ссылок на нормы удаляются перед проверкой. Непроверенное число не изменяет proposal или
расчёт: `provenance_ok=false`, число перечисляется в `unverified_numbers`, а UI показывает
явное предупреждение и не представляет reply как проверенный.

## 15.7 Клиентское применение

Studio хранит полученный proposal отдельно от `PROJ`. «Применить» сначала сохраняет
глубокую undo-копию, затем применяет ровно нормализованные ops через клиентский путь,
вызывает `projSet` и свежий `project-report`. «Отклонить» удаляет proposal без мутации.
Undo восстанавливает сохранённый канонический проект и также запускает пересчёт.

Share-экран остаётся read-only и не содержит Copilot или mutation controls. Все новые
экраны сохраняют data identity, provenance, дисклеймер и `UNSIGNED_ADVISORY`.
