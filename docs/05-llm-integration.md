# 05 — Интеграция LLM (Gemini через OpenRouter)

## 5.1 Доступ

OpenRouter — OpenAI-совместимый шлюз. Клиент (`llm/client.py`) на `httpx`:

- Endpoint: `POST {OPENROUTER_BASE_URL}/chat/completions`.
- Заголовки: `Authorization: Bearer $OPENROUTER_API_KEY`, `HTTP-Referer`, `X-Title`.
- Тело: `{model, messages:[{role:system},{role:user}], response_format?}`.
- Таймаут: `ELECTRICOPILOT_LLM_TIMEOUT` (по умолчанию 60 с).

**Маршрутизация моделей (slug'и подтверждены live, `list_models.py`):**
- `ELECTRICOPILOT_MODEL_STRONG` = `google/gemini-3.1-pro-preview` — рассуждение и **независимая
  проверка**.
- `ELECTRICOPILOT_MODEL_FAST` = `google/gemini-3-flash-preview` — разбор NL-ввода и нарратив.

**Reasoning-модель (эмпирически подтверждено).** Сильная модель тратит токены на скрытое
рассуждение (`message.reasoning`); при малом `max_tokens` `message.content` приходит пустым
(`finish_reason='length'`). Поэтому клиент: (а) ставит щедрый `max_output_tokens` (дефолт 2048);
(б) при пустом `content` поднимает `LlmError`, а не молча возвращает `""`. Контент читается из
`choices[0].message.content`.

**Обработка ошибок (D10):** при неизвестном slug'е / 4xx о модели — `LlmConfigError` с
явным текстом (не молчаливый фолбэк). Точные slug'и подтверждаются `scripts/list_models.py`
и командой `electricopilot models`.

## 5.2 Роли и структурированный вывод

Везде, где LLM возвращает данные, используем `response_format` со схемой (JSON), чтобы
получить валидируемый объект, а не свободный текст.

### R1. Intake (Flash) — NL → `SizingRequest`
- Вход: свободное описание нагрузки/условий. Выход: JSON по схеме `SizingRequest`.
- Модель **не считает** — только извлекает параметры. Пустые поля остаются пустыми →
  инженер подтверждает/дополняет. Нет ключа → роль недоступна, используется строгий ввод.

### R2. Explain (Flash, при сложности — Pro) — `AuditTrace` → нарратив
- Вход: полный `SizingResult` (числа уже посчитаны). Выход: человекочитаемое объяснение,
  **опирающееся только на числа из трассы**. Промпт прямо запрещает вводить новые числа.
- Фолбэк без ключа: детерминированный шаблонный рендер трассы (`explain.render_template`).

### R3. Verify (Pro) — независимая критика
- Вход: `SizingRequest` + `SizingResult`. Задача: независимо перепроверить условия
  координации, поправки, ВП, адиабатику; вернуть `VerificationVerdict{agrees, issues}`.
- **Всегда** параллельно выполняется детерминированная проверка инвариантов
  (`verify.deterministic_check`) — она не зависит от LLM и заполняет `deterministic_ok`.

## 5.3 Гардрейл числового провенанса (guardrails.py)

1. Собрать «разрешённое множество» чисел **только из типизированных числовых полей**
   `SizingResult` (IB, In, It, ∏k, IZ, S, ΔU, %, I2, S_min, пределы, входы, числовые значения
   в `inputs/result` шагов) + малый структурный whitelist (1,2,3,1.45,1.6,√3,100). Свободный
   текст (`computation/detail`) и строки цитат **не** участвуют — иначе ряд номиналов и id
   цитат засоряли бы множество (найдено ревью).
2. Из текста LLM **вырезать ссылки на нормы** (`IEC 60364-4-43`, `§433.1`, `B.52.14`, точные
   строки цитат результата), затем извлечь числовые токены — с поддержкой разрядов через
   пробел (`25 000` → одно число, а не `25`+`000`).
3. Каждое оставшееся число должно матчиться разрешённому (допуск ±0.05 / ±1 %). Непокрытые →
   `unverified_numbers`.
4. При `ELECTRICOPILOT_STRICT_PROVENANCE=true` и непустом списке: `provenance_ok=False`,
   `apply_provenance_downgrade` возвращает копию с `overall_status='NEEDS_REVIEW'` **только если
   был `PASS`** (провал провенанса не смягчает `FAIL` — иначе провал маскировался бы); нарратив
   помечается непроверенным (числа из трассы остаются истиной; ненадёжен только текст).

Тем самым LLM не может «протащить» ложное число мимо аудита.

## 5.4 Промпты (каркас, полный текст — в коде)

- **System (общий):** «Ты — ассистент проектировщика электрики. Ты НЕ придумываешь числа.
  Все числовые значения берутся исключительно из предоставленной трассы/запроса. Твоя роль —
  разбор/объяснение/проверка. Ты не сертифицируешь; итог требует подписи инженера.»
- **R1 user:** описание + JSON-схема `SizingRequest` + требование не заполнять недостающее.
- **R2 user:** сериализованный `SizingResult` + «объясни выбор, ссылаясь на пункты норм из
  трассы; НЕ вводи новых чисел».
- **R3 user:** `SizingRequest` + `SizingResult` + «независимо перепроверь условия; верни
  agrees/issues; если видишь нарушение IB≤In≤IZ, I2≤1.45·IZ, ВП, адиабатики — перечисли».

## 5.5 Стоимость/скорость

- Flash — дёшево/быстро (интейк, черновой нарратив). Pro — дороже (проверка/сложное
  объяснение). Ретраи: 1 повтор на сетевые/5xx, без повтора на `LlmConfigError`.
- В фолбэк-режиме LLM не вызывается вовсе (нулевая стоимость), функциональность ядра полна.
