## 0. Правила работы исполнителя (обязательны для каждой фазы)

1. **Числа рождает только детерминированный код.** LLM разбирает текст, объясняет,
   маппит колонки — но никогда не вычисляет и не «вспоминает» инженерные значения.
2. **ЗАПРЕТ на нормы из памяти модели.** Любое числовое значение норм-таблиц (токи,
   коэффициенты, пределы) вносится ТОЛЬКО из источника (PDF/скан/текст), предоставленного
   заказчиком, с указанием документа и таблицы. Нет источника → остановись и запроси у
   заказчика. Нарушение этого правила обесценивает весь продукт.
3. **Spec-first:** изменение контрактов (`models.py`, схемы API) сначала фиксируется в
   docs (03 или соответствующий doc фазы), потом в коде.
4. Перед каждым коммитом: `uv run pytest && uv run ruff check . && uv run mypy src` — всё
   зелёное. Тесты офлайн (без сети/ключей), LLM — через fake-клиент (см. `tests/test_llm_fallback.py`).
5. **Стек не менять:** фронт остаётся vanilla JS (без React/сборщиков), бэк — FastAPI,
   структура `src/electricopilot/*`. Стиль кода — как в соседних файлах (docstring-и на
   английском, пользовательские строки на русском).
6. Каждая фаза — отдельная ветка `feat/v3-phase-N-<slug>` от `main`, PR с описанием.
   Внутри фазы — атомарные коммиты по чек-листу.
7. Каждая фаза завершается: обновлением docs (см. фазу), README (если видимо пользователю),
   ручным демо-сценарием через Studio (описан в фазе).
8. Дисклеймеры/провенанс: любой новый экран и документ несёт статус данных
   (`illustrative`/`public_standard`) и `UNSIGNED_ADVISORY` — как существующие.

Порядок фаз: **0 → 1 → 2 → 3a → 3b → 4 → 5 → 6**. Фазу 4 можно вести параллельно с 3.

## Фаза 1 — Мульти-пак норм и реальные данные ГОСТ/СТ РК (≈2 сессии + ввод данных с заказчиком)

**Ключевое решение.** Целевой рынок фазы — Казахстан. Источники (проверено 2026-07-02):

- **ПУЭ РК** — Правила устройства электроустановок, утв. приказом Министра энергетики РК
  от 20.03.2015 № 230, **действующие**, полный текст с ~250 HTML-таблицами (включая все
  таблицы допустимых длительных токов и поправочных коэффициентов) лежит **бесплатно** на
  официальном правовом портале: https://adilet.zan.kz/rus/docs/V1500010851 .
  Значения машинно-извлекаемы прямо из HTML.
- **СТ РК IEC 60364-x** — казахстанская адаптация IEC 60364 (часть 1 — СТ РК IEC
  60364-1-2012 и др.); тексты продаются в официальном магазине КазСтандарта
  (new-shop.ksm.kz), недорого. Часть 5-52 структурно 1:1 ложится на движок (методы A1…G).
- СН РК 4.04-07-**2019** «Электротехнические устройства» (редакция 2013 утратила силу —
  не перепутать).

Методология движка (IB≤In≤IZ, I2≤1.45·IZ, адиабатика, ΔU) — IEC 60364; движок НЕ меняется.
Путь данных: **основной пак `pue-rk` из бесплатного ПУЭ РК** + (опционально, при покупке
документа) пак `st-rk-iec-60364` как структурно-идеальный. Нюанс маппинга для `pue-rk`:
таблицы ПУЭ структурированы «в воздухе / в земле / в трубе» по маркам кабелей, а движок —
методами прокладки A1…G. Соответствие фиксируется в паке явно (например: «в воздухе» → C,
«в трубе» → B1, «в земле» → D) и документируется в `_citation.note` каждой таблицы; методы
без покрытия в ПУЭ в этом паке отсутствуют (off-table политика движка уже даёт честную
ошибку). ГОСТ Р 50571.x (Россия) — тот же механизм, отдельный пак, отложено.

### 1.1 Механизм мульти-пака

- Переместить `data/iec_stub.json` → `data/packs/iec-stub.json` (имя пакета = имя файла).
- `loader.py`: `load_data_pack(name_or_path)` — если аргумент без `/` и `.json` →
  резолвить из `data/packs/`; `@lru_cache` по имени (сохранить текущий фолбэк-резолвинг
  через `importlib.resources` и `__file__` — он нужен Vercel). Функция
  `list_packs() -> list[DataPackMeta]`.
- `models.py`: `DataStatus = Literal["illustrative", "public_standard", "licensed"]`;
  в `DataPackMeta` добавить `source_document: str | None`. Новый текст
  `PROVENANCE_NOTE_PUBLIC` («значения внесены из публичного государственного стандарта
  <…>, транскрипция проверена инженером <ФИО/дата>; документ не воспроизводится целиком»).
  Отразить в docs/03 и docs/04.
- В JSON каждая таблица получает в `_citation` поля `source_document`, `source_table`,
  `entered_by`, `verified_by` (строки, могут быть пустыми до проверки).
- API: `GET /api/packs` → `[{name, version, status, source_note}]`; query-параметр
  `?pack=<name>` у `/api/size`, `/api/viz`, `/api/explain`, `/api/verify`; у проекта —
  поле `norm_pack` (используется в `/api/project-report` и всех экспортных эндпоинтах).
  `SizingRequest` не трогаем (замороженный контракт) — пак передаётся рядом.
- UI: селектор пакета в шапке щита (сохраняется в проект); бейдж статуса данных
  (`синтетические` жёлтый / `публичный стандарт` зелёный) в advisory-строке и отчётах.

### 1.2 Протокол ввода реальных данных (человек в контуре)

1. Источник для `pue-rk` — официальная страница Әділет (URL выше). Исполнитель скачивает
   HTML и извлекает нужные таблицы КОДОМ (скрипт `scripts/extract_pue_rk.py`: парсинг
   HTML-таблиц → черновик пакета), а не переписыванием по памяти. URL источника и номер
   таблицы («Таблица N») пишутся в `_citation` каждой таблицы. Для СТ РК (если куплен) —
   заказчик передаёт официальный PDF.
2. Результат — `data/packs/pue-rk.json` (`status: "public_standard"`).
3. **ВНИМАНИЕ: в официальном HTML Әділет встречаются опечатки** (обнаружены при разведке:
   «216» в ряду 175-215-…-300 вместо ожидаемых ~260; «2260» вместо ~260). Поэтому
   `scripts/pack_review.py` обязан, помимо печати таблиц для сверки глазами:
   (а) проверять монотонность допустимого тока по сечению в каждой колонке;
   (б) проверять монотонность поправочных коэффициентов по температуре/количеству;
   (в) помечать выбросы (скачок > 60% между соседними сечениями) как подозрительные.
   Подозрительные значения сверяются с печатной редакцией ПУЭ и решением заказчика.
4. Golden-кейсы: добавить в `tests/test_golden_cases.py` параметризацию по пакету;
   опорные значения для нового пака пересчитать НЕЗАВИСИМО через `scripts/reference_calc.py`
   (расширить его чтением произвольного пакета), а не скопировать из вывода движка.

**DoD:** оба пака валидируются; выбор пака работает в CLI (`--data-pack pue-rk`),
API и Studio; в отчёте видны цитаты на ПУЭ РК (приказ № 230, номер таблицы) и статус
`public_standard`; docs/04 описывает протокол ввода. Демо: один и тот же щит на паках
`iec-stub` и `pue-rk`, различия видны.

## Фаза 2 — «Проект за вечер»: генерация документации (≈3 сессии)

**Цель:** из модели щита кнопкой получить: однолинейку (SVG + DXF), кабельный журнал
(XLSX), спецификацию (XLSX), отчёт (MD) — одним zip-архивом. Это главный wow продукта.

### 2.1 Архитектура экспорта

Новый пакет `src/electricopilot/export/`:

- `primitives.py` — плоская геометрическая модель: `Line`, `Polyline`, `Rect`, `Text`
  (координаты в мм, слой, стиль). **Единственный источник геометрии** — рендереры тупые.
- `symbols.py` — библиотека условных обозначений (упрощённо по ГОСТ 2.755): автомат (QF),
  УЗО/АВДТ, предохранитель, шина, стрелка нагрузки, рамка листа со штампом-заглушкой.
  Каждый символ — функция `(x, y, …) -> list[Primitive]`.
- `sld.py` — layout однолинейки: `build_sld(project, report) -> list[Primitive]`.
  Лист A3 альбомный (420×297). Ввод слева → горизонтальная шина → отходящие линии
  вертикальными колонками; на линии сверху вниз: аппарат (тип/In/кривая), УЗО (если есть),
  подпись кабеля (марка-заглушка, сечение, длина), IB/ΔU, имя цепи, статус (цвет).
  Если цепей больше, чем влезает (~16 на лист), — разбивка на несколько листов.
- `svg.py` — `primitives -> str` (SVG); используется и для предпросмотра в Studio.
- `dxf.py` — `primitives -> bytes` через **ezdxf** (новая core-зависимость, чистый Python,
  MIT; добавить в `pyproject.toml` и `requirements.txt`). Слои: `FRAME`, `BUS`, `WIRES`,
  `SYMBOLS`, `TEXT`. Текст — шрифт по умолчанию, кириллица в UTF-8 (DXF R2010+).
- `cable_journal.py` — кабельный журнал по мотивам формы ГОСТ 21.613: колонки
  «Обозначение | Начало | Конец | Марка (заглушка) | Сечение | Длина по проекту, м |
  Длина с запасом, м | Способ прокладки». Запас — коэффициент из настроек проекта
  (по умолчанию 1.05, поле `project.export_settings.cable_margin`).
- `boq.py` — спецификация: группировка одинаковых аппаратов (класс+In+кривая+УЗО) и
  кабелей (сечение+материал+изоляция) → позиции с количеством (шт/м).
- `xlsx.py` — рендер журнала/спецификации в XLSX через **openpyxl** (новая зависимость).
- `bundle.py` — `build_bundle(project) -> bytes`: zip в памяти (`io.BytesIO`) с
  `report.md`, `sld.dxf`, `sld.svg`, `cable_journal.xlsx`, `boq.xlsx`, `project.json`.
  Каждый документ включает дисклеймер и провенанс-ноту пакета данных.

### 2.2 API и UI

- `POST /api/project-export` `{project}` → `application/zip` (имя файла из `board_ref`).
- `POST /api/project-sld` `{project}` → `{svg: str, sheets: int}` — предпросмотр.
- UI (экран щита): кнопка «📦 Пакет документов», вкладка «Однолинейка» с SVG-предпросмотром.
- Печать: маршрут `#/p/<id>/print` — печатная страница (schedule + итоги + однолинейка
  + трасса), `@media print` CSS; PDF получается браузерным «Сохранить как PDF».
  **Серверный PDF не делаем** (тяжёлые зависимости в serverless не тянуть).

### 2.3 Тесты

- Golden-тест SVG: нормализованный вывод (без плавающих id) сравнивается со снапшотом.
- DXF round-trip: сгенерировать → прочитать ezdxf-ом → проверить слои, количество
  entity, наличие ключевых текстов (ref цепей, In, сечения).
- XLSX: прочитать openpyxl-ом, проверить заголовки и строки против report.rows.
- Bundle: zip открывается, все 6 файлов на месте, размеры > 0.

**DoD:** демо-сценарий — «Щит ВРУ-1 (пример)» → пакет документов скачивается, DXF
открывается в бесплатном вьюере (ODA/LibreCAD), журнал и спецификация согласованы с
panel schedule. docs: новый `docs/13-document-export.md` (формы, layout-правила, ограничения).

## Фаза 3a — Нормоконтроль: движок правил (≈2 сессии)

**Цель:** кнопка «Нормоконтроль» на щите → список findings со ссылками на пункты норм.
Это же — фундамент будущего b2b-продукта «экспертиза как CI».

### Архитектура

Новый пакет `src/electricopilot/normcheck/`:

- `models.py`:
  ```python
  Severity = Literal["error", "warning", "info"]
  class Finding(BaseModel):
      rule_id: str; severity: Severity
      scope: Literal["circuit", "board"]; circuit_id: str | None = None
      title: str; detail: str
      observed: dict[str, Any]; required: dict[str, Any]
      citation: Citation
  ```
- `rules.py` — каждое правило: чистая функция `(ctx: BoardContext) -> list[Finding]`,
  регистрация декоратором `@rule("R…")`. `BoardContext` собирается runner-ом: project,
  пересчитанные `SizingResult` каждой цепи, report/board-итоги, data pack.
- **Пороги и таблицы правил — в дата-паке** (новый раздел `normcheck` в JSON со своими
  `_citation`), не в коде. Для `iec-stub` — синтетические, для `gost-r-50571` — по
  протоколу фазы 1.2.
- `runner.py`: `run_normcheck(project, pack) -> list[Finding]` (сортировка: severity,
  затем circuit ref).

### Стартовый набор правил (расширяемый)

| ID | Правило | Severity |
|---|---|---|
| R01 | Цепь со статусом FAIL (с governing-критерием) | error |
| R02 | Розеточная цепь (`purpose=socket`) без УЗО ≤30 мА | error |
| R03 | Кумулятивное ΔU: питающая линия + цепь > лимита (нужно опц. поле `supply.feeder = {length_m, section_mm2, material}`) | error |
| R04 | Селективность по номиналу: In вводного аппарата ≤ In отходящей (нужно опц. поле `supply.incomer = {device_class, In_a}`) | warning |
| R05 | Перекос фаз выше порога из пака | warning |
| R06 | Резерв мест щита ниже порога из пака | warning |
| R07 | Кривая B на двигательной нагрузке (пусковые токи) | warning |
| R08 | Al сечением ниже минимума из пака | error |
| R09 | КЗ-проверка пропущена (Iscc не задан) | warning |
| R10 | Сечение PE: S_pe по таблице пака (54-я серия) vs заглушка в проекте | info |

Каждое правило обязано ссылаться на конкретный пункт (в `iec-stub` — со статусом
illustrative; реальные пункты вносятся при заполнении gost-пака).

### API, UI, LLM

- `POST /api/normcheck` `{project}` → `{findings: [...], summary: {errors, warnings, infos}}`.
- UI: вкладка «Нормоконтроль» на экране щита — список findings с severity-бейджами,
  клик по finding → переход в редактор цепи; маркеры на строках schedule.
- LLM-роль (опционально, при ключе): `narrate_findings` — связный абзац «что не так и
  почему», через существующий гардрейл провенанса (числа — только из findings/result).

**DoD:** демо — в примере «Щит ВРУ-1» испортить цепь (убрать УЗО с розеток, удлинить
кабель) → нормоконтроль находит и объясняет. Тесты: по 1-2 теста на правило (позитив +
негатив), тест сортировки, тест «пороги берутся из пака». docs: `docs/14-normcheck.md`.

## Фаза 3b — Импорт чужого щита (XLSX/CSV) (≈1-2 сессии)

**Цель:** «проверь чужой щит» — загрузка готовой таблицы щита → черновик проекта →
пересчёт движком → findings + diff «в проекте / по расчёту».

- `POST /api/import-schedule` (multipart, XLSX/CSV ≤ 1 МБ) →
  `{ok, project_draft, mapping, issues[]}`.
- Парсинг файла — код (openpyxl/csv). **LLM маппит только заголовки колонок** на
  канонический словарь полей (`ref, description, power_kw, voltage, phases, pf, length,
  device, In, curve, rcd, cable_section, material, insulation, method`); значения ячеек
  копирует код без участия LLM. Без ключа — эвристика по словарю синонимов
  (рус/англ: «Мощность», «P, кВт», «kW»…), словарь в коде.
- Незамапленные обязательные поля → `issues[]`, заполняются дефолтами проекта с пометкой
  `assumed` (показать жёлтым в UI).
- Diff-отчёт: для каждой цепи «заявлено в файле» (сечение/In) vs «требуется по расчёту» —
  это просто спец-режим normcheck (правило R11: заявленное сечение < расчётного → error;
  заявленный In ≠ подобранному → warning).
- UI: на дашборде кнопка «Импортировать щит (XLSX/CSV)» → экран проверки маппинга
  (таблица: колонка файла → поле, селекты для ручной правки) → «Создать проект».
- Тесты: 3 фикстуры-файла (аккуратный XLSX, кривой CSV с русскими заголовками, файл с
  пропусками) → маппинг эвристикой, diff-правила.

**DoD:** демо — реальный кабельный журнал/щитовая таблица заказчика импортируется и
проверяется. docs/14 дополняется разделом «Импорт».

## Фаза 4 — Персистентность (Neon) и share-ссылки (≈2 сессии)

**Цель:** проекты живут не только в localStorage; расчётом можно поделиться ссылкой.

- Хранилище: абстракция `src/electricopilot/store.py` — протокол
  `ProjectStore` (list/get/put/delete/share) c двумя реализациями:
  `MemoryStore` (тесты) и `PostgresStore` (psycopg3, короткие соединения без пула —
  serverless-friendly; `DATABASE_URL` уже в конфиге). Таблицы:
  `projects(id text pk, workspace text, name text, data jsonb, updated_at timestamptz)`,
  `shares(token text pk, project_id text, created_at)`. Миграция — `scripts/init_db.py`
  (идемпотентный `CREATE TABLE IF NOT EXISTS`).
- Auth-модель (осознанно минимальная, зафиксировать в docs): анонимный
  `workspace_id` из localStorage (он уже есть — `ec_v2_workspace`) передаётся заголовком
  `X-Workspace`. Это не безопасность, это разграничение — написать честно в docs.
- API: `GET/PUT/DELETE /api/projects[/{id}]`, `POST /api/projects/{id}/share` → `{token}`,
  `GET /api/shared/{token}` → проект read-only. Без `DATABASE_URL` эндпоинты отвечают
  `{ok: false, error: "no_db"}` и UI работает как сейчас (graceful degradation).
- Фронт: localStorage остаётся источником скорости/офлайна; фоновая синхронизация
  (debounce 2 с после `projSet`), стратегия конфликтов — last-write-wins по `updated_at`
  + тост «проект обновлён с другого устройства». Read-only маршрут `#/s/<token>`
  (скрыть кнопки редактирования).
- Тесты: `MemoryStore` покрывает контракт; `PostgresStore` — только smoke-тест под
  `@pytest.mark.skipif(not DATABASE_URL)` (в CI не бежит).

## Фаза 5 — Copilot-агент щита с инструментами («что-если») (≈2 сессии)

**Цель:** чат на уровне щита: «добавь конвейер 7,5 кВт на L2 и проверь ввод» → агент
планирует, движок считает, пользователь видит diff и жмёт «Применить».

- Новый пакет `src/electricopilot/copilot/`:
  - `tools.py` — JSON-описания инструментов для function calling (OpenRouter/Gemini):
    `get_board_state()`, `parse_circuit(text) -> request` (реюз intake),
    `compute(request) -> result-summary`, `run_normcheck()`,
    `propose_changes(ops: [{op: add|edit|delete, circuit_id?, request?, meta?, ref?}])`.
  - `loop.py` — цикл: `POST /chat/completions` c `tools`, исполнение вызовов, максимум
    6 итераций, суммарный таймаут 45 с (лимит Vercel 60). Ошибка/лимит → честный ответ
    «не смог, вот что успел».
- **Инвариант безопасности:** сервер НИКОГДА не мутирует проект. `propose_changes`
  завершает цикл и возвращает `proposal`; diff считается детерминированно: пересчёт
  «до» и «после» движком (`project-report` × 2) → таблица изменений по затронутым цепям
  (S, In, IB, ΔU, статус) и по итогам щита (кВт, перекос, ввод). Числа в тексте ответа
  агента проходят провенанс-гардрейл против ОБОИХ состояний.
- API: `POST /api/copilot` `{project, message, history[]}` →
  `{reply, proposal: {ops, diff} | null, model}`. Без ключа — вежливый отказ с
  подсказкой, что работает (intake недоступен, но ручное редактирование и normcheck — да).
- UI: чат-панель на экране щита (не только в редакторе цепи); карточка proposal с
  diff-таблицей и кнопками «Применить» / «Отклонить»; применение — существующие
  клиентские операции + `projSet` + пересчёт.
- Тесты: fake-клиент со заскриптованной последовательностью tool calls (по образцу
  `test_llm_fallback.py`): сценарий «добавь цепь» → proposal с корректным diff; сценарий
  превышения лимита итераций; провенанс-фейл в reply → пометка.

**DoD:** демо — три сценария: добавить цепь, «что будет если удлинить M1 до 80 м»,
«почему статус FAIL». docs: `docs/15-copilot-tools.md` (контракт инструментов, инварианты).

## Фаза 6 — Каталог оборудования (≈1-2 сессии, после фаз 2-3)

**Цель:** от абстрактного «MCB 32 A» к реальному артикулу — и почва для монетизации.

- `src/electricopilot/catalog/`: `schema.py`
  (`CatalogItem {sku, vendor, series, kind: mcb|rcbo|fuse|cable, In_a?, curve?, icu_ka?,
  poles?, section_mm2?, cores?, unit, provenance: {source, retrieved}}`),
  `loader.py` (JSON-файлы из `data/catalogs/`), `select.py` — детерминированный подбор:
  фильтр по типу, In, кривой, полюсам (из phases), `icu_ka ≥ Iscc`; сортировка по series.
- **Данные вводит заказчик** из открытых каталогов производителей (стартово: 2-3 серии
  MCB/RCBO одного-двух вендоров + пара кабельных марок). Исполнитель готовит схему,
  скрипт-валидатор `scripts/catalog_check.py` и шаблон; SKU из памяти модели не выдумывать
  (правило 0.2 действует).
- API `POST /api/catalog-select` `{request | result}` → `{candidates: [...]}`. UI: в
  редакторе цепи блок «Аппарат из каталога» (кандидаты, выбор сохраняется в
  `circuit.meta.selected_sku`); `boq.py` (фаза 2) подставляет SKU в спецификацию.

**DoD:** демо — спецификация щита с реальными артикулами. docs/16.
