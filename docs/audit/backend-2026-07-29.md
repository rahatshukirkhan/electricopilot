## C1. Параметр норм-пака читает произвольные файлы сервера и валит воркер по памяти [П]

`data/loader.py:365-386`: `_is_pack_name()` считает «путём» любую строку с `/` или `.json`,
и тогда `load_data_pack` делает `Path(path).read_text()`. Это фича CLI из docs/12 §1.1,
но она проброшена в HTTP: `studio_api.py:202-206` берёт `pack` из query-строки, а
`project.norm_pack` (`project_contract.py:161` — просто `str | None`) приходит в теле.
Валидации против `list_packs()` нет ни в одном месте.

Затронуты без аутентификации: `/api/size`, `/api/viz`, `/api/explain`, `/api/verify`,
`/api/normcheck`, `/api/project-report`, `/api/project-sld`, `/api/project-export`,
`/api/import-schedule`, `/api/copilot`.

Что подтверждено на **проде** (три безвредных запроса):

```
POST /api/size?pack=/etc/hosts
→ 400 {"detail":"failed to load data pack from /etc/hosts: Extra data: line 1 column 8"}

POST /api/size?pack=/var/task/vercel.json
→ 400 {"detail":"... 13 validation errors for DataPack ...
      input_value={'version': 2, 'builds': ...st': 'web/index.html'}]}, input_type=dict]"}
```

То есть файл действительно читается, и для JSON-файлов часть содержимого возвращается
клиенту в тексте ошибки pydantic. Масштаб раскрытия ограничен: pydantic обрезает
`input_value` до префикса и суффикса — в контрольной пробе с подложенным файлом секрет
целиком **не** утёк (`SECRET_VISIBLE: False`). Практически это оракул существования и типа
файла (разные сообщения для «нет файла» / «не JSON» / «JSON не той схемы») плюс частичное
раскрытие содержимого JSON.

Более тяжёлая половина — ресурсы. Локальная проба `?pack=/dev/zero`:

```
t= 2c  RSS=1579.0 МБ (старт 93.8 МБ)  ответ=ещё читает
t=10c  RSS=1579.0 МБ                  ответ=ещё читает
```

Один неаутентифицированный запрос заставляет воркер читать бесконечный поток: локально
RSS вырос с 94 МБ до 1,6 ГБ за ~2 с и ответ не пришёл. На Vercel это OOM/тайм-аут функции
(`maxDuration=60`) на каждый такой запрос. На проде этот вариант намеренно **не** запускался.

Направление лечения (не применялось): резолвить `pack` только из `list_packs()` на границе
API; путь к файлу оставить CLI. Побочно уйдёт и утечка текста ошибки в `_pack_or_400`.

## H1. В проде нет таблиц `projects`/`shares` — весь project/share API отвечает 500 [П]

Запрос к проду:

```
GET /api/projects   -H "X-Workspace: ws_00000000"   → 500 Internal Server Error
```

Read-only проверка боевого Neon показала причину:

```
таблицы: ['norm_documents', 'norm_links', 'norm_sections', 'sizing_sessions']
PostgresStore.list() → UndefinedTable: relation "projects" does not exist
```

Это та же база, что обслуживает прод: `GET /api/norms` на проде отдаёт документ ПУЭ с
7791 секцией, то есть проверенный мной Neon — именно тот, к которому ходит функция. Значит
альтернативные объяснения 500 («другая БД», «psycopg не попал в бандл») исключены.

Норм-таблицы создаются сами (`norms/ingest.py:114` вызывает `store.init_schema()`), а
схема проектов создаётся только вручную через `scripts/init_db.py` — этот шаг на проде не
выполнен. При этом `/api/health` рапортует `"project_store":"neon"` (оно смотрит лишь на
наличие `DATABASE_URL`), фронт по этому признаку ставит `SYNC_AVAILABLE = true`
(`web/app.js:1000`) и начинает синхронизацию, которая гарантированно падает. То есть
заявленная в CLAUDE.md как закрытая фаза 4 (Neon-персистентность и share) в проде не работает.

Сопутствующее: неинициализированная схема даёт голый 500 вместо типизированной ошибки —
`_project_store()` не отличает «БД не настроена» от «БД недоступна».

## H2. 32-битные идентификаторы + гонка в `PostgresStore.put` [П + В]

`web/app.js:9`: `uid = p => p + '_' + crypto.randomUUID().slice(0, 8)` — 8 hex-символов,
т.е. 32 бита энтропии, и для `ws_`, и для `prj_`, и для `ckt_`. Это [П] (код фронта).

Следствия:

1. `docs/15` §15.2 честно называет `X-Workspace` разграничением, а не аутентификацией, но
   разграничение опирается на неугадываемость id. При 32 битах вероятность коллизии двух
   рабочих областей достигает ~50% на ~77 тыс. областей и уже заметна на тысячах —
   пользователь при коллизии видит и правит чужие проекты.
2. `projects.id` — глобальный PRIMARY KEY на всю таблицу, не пара (workspace, id).
   Коллизия id проекта между двумя владельцами приводит к `ProjectNotFoundError` (404)
   у законного второго владельца при сохранении.
3. **[В]** Гонка в `store.py:199-232`: `SELECT ... FOR UPDATE` на несуществующей строке
   ничего не блокирует. Два одновременных PUT с одинаковым `project.id` из разных
   workspace: обе транзакции видят `row = None`, обе идут в
   `INSERT ... ON CONFLICT (id) DO UPDATE SET name, data, updated_at` — вторая перезаписывает
   содержимое чужого проекта (владение сохраняется, так как `workspace` в `SET` не входит).
   Проверка принадлежности workspace при этом обходится. На живом Neon сценарий не
   воспроизводился — вывод из кода. Слабый генератор id делает эту гонку достижимой без
   подбора.

4. **[В]** Туда же — `_reject_stale` (`store.py:95-99`) разрешает конфликты по
   `updated_at`, который присылает клиент. Snapshot с датой в будущем выигрывает
   last-write-wins навсегда и блокирует последующие законные записи владельца (409 на
   каждую). Ошибка часов клиента даёт тот же эффект без злого умысла.

Лечение: полный `crypto.randomUUID()`, `ON CONFLICT ... WHERE
projects.workspace = EXCLUDED.workspace` (либо advisory lock на id), серверная отметка
времени как арбитр вместо клиентской.

## M2. `/api/explain` не применяет понижение статуса по провенансу [В]

docs/05 §5.3 п.4 (замороженная спека) требует: при непустых `unverified_numbers` в strict-режиме
`apply_provenance_downgrade` понижает `PASS` → `NEEDS_REVIEW`. В HTTP-пути
(`studio_api.py:261-275`) провенанс считается, кладётся в нарратив, но даунгрейд не
применяется — возвращается исходный `result.overall_status`. Функция вызывается только в
`pipeline.py:72` (CLI). Фронт (`web/app.js:822`) `overall_status` из этого ответа не читает
вовсе, показывает лишь тег «провенанс FAIL».

Сценарий: модель протаскивает непроверенное число → в CLI расчёт помечается NEEDS_REVIEW,
через Studio тот же расчёт остаётся PASS. Один расчёт, два статуса в зависимости от точки
входа — для продукта, который продаёт аудируемость, это содержательное расхождение, а не стиль.

## M2b. Гардрейл провенанса собирает числа из прозы трассы вопреки той же спеке [В]

Это второе, независимое расхождение в той же цепочке — и оно сидит на самом механизме,
которым обеспечивается принцип №1 (числами владеет детерминированное ядро).

docs/05 §5.3 п.1: «Свободный текст (`computation/detail`) и строки цитат **не** участвуют —
иначе ряд номиналов и id цитат засоряли бы множество (найдено ревью)». Формулировка появилась
2026-07-02 в коммите `308c207` «Harden numeric-provenance guardrail», где код и спеку правили
вместе — то есть ограничение вводилось осознанно, по итогам состязательного ревью.

`guardrails.py:80-89` сегодня делает ровно обратное:

```python
for st in result.audit_trace:
    for s in (st.formula, st.computation):
        if s: _harvest_text(s, allowed)
for ch in result.checks:
    _harvest_text(ch.condition, allowed)
    _harvest_text(ch.detail, allowed)
```

Регрессию внёс `8261a14` («Studio v1»), докстринг функции её прямо декларирует: «Typed numeric
leaves + numbers from AUDIT prose (formula/computation/detail/condition)». Спека с тех пор не
менялась (в истории `docs/05-llm-integration.md` всего два коммита: заморозка и `308c207`).

Эффект: разрешённое множество шире предписанного — в него попадает всё, что `sizer.py:104-136`
форматирует в текст (`IB=…`, `1.45·IZ=…`, `req_IZ≥…`, `предел …%`, `S_min=…`), и каждое
сравнение идёт с допуском ±0.05/±1%. Чем шире множество, тем выше шанс, что подложенное
моделью число случайно совпадёт с разрешённым и пройдёт как проверенное. Обоснование в
докстринге (производные вроде `1.45·IZ` в типизированных полях отсутствуют) выглядит
разумным — но тогда решение должно быть зафиксировано в спеке, а не жить вопреки ей.

Это развилка для владельца, а не однозначный баг: либо вернуть код к §5.3 п.1, либо
осознанно переписать §5.3 (спека заморожена — правка требует вашего решения).

## L4. `.env` репозитория подхватывается независимо от рабочего каталога [П]

## Проверено и НЕ подтвердилось

- **SQL-инъекции** — во всех запросах (`store.py`, `norms/store.py`) параметры передаются
  через placeholders, включая FTS-запрос через `websearch_to_tsquery(%(query)s)`. Чисто.
- **Traversal в читалке норм.** `JsonNormStore._path` конкатенирует `doc_id` в путь, но
  маршрут Starlette не пропускает `/` в path-параметре — `../../secret` и его
  percent-encoded варианты дают 404 маршрутизатора. Не находка.
- **Утечка ключей в ответах.** `OPENROUTER_API_KEY` живёт только в заголовке запроса к
  OpenRouter; тексты ошибок провайдера (обрезанные до 300 символов) в ответ API не
  просачиваются, кроме сообщения copilot `model_error`, где секрета нет.
- **SSRF через fetcher норм.** `norms/fetch.py` строит URL из `doc_id`, а сам ingest
  доступен только из CLI и закрыт реестровым гейтом (`registry.require_entry`). Из HTTP
  fetch не вызывается.
- **Инъекция через тексты норм в LLM.** Реранк (`norms/search.py`) принимает от модели
  только точную перестановку выданных id — любой посторонний ответ отбрасывается целиком.
- **Производительность детерминированного слоя.** 128 цепей: project-report 0,07 с,
  +SLD 0,09 с, normcheck 0,09 с, экспорт zip 0,20 с. Роста хуже линейного нет.
